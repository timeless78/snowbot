앱명 / 프로젝트명

스노봇 커넥트(SnowBot Connect) — 차와 감성 봇을 잇는 앱

1. 앱 한 줄 소개 바뀜

대시보드 위 감성 봇을 차에 연결하는 커넥트 앱. 차가 주는 정보와 봇이 느낀 정보를 AI 로 해석해 봇의 몸에 맞는 표정과 목소리로 돌려준다. 열린 연결 규약으로 어떤 봇이든 붙을 수 있고, 첫 번째 봇은 눈사람 로봇 스노봇이다.

2. 기획 배경

주목한 순간: 혼자 운전할 때

혼자 운전할 때 생기는 일옆자리에 사람이 있으면
졸음이 와도 혼자서는 모르고 버팁니다. 고속도로 사망사고의 절반 이상이 졸음·전방주시 태만입니다(서울시 미디어허브)"너 졸려 보여, 쉬었다 가자"
계기판에 낯선 경고등이 켜지면 뭔지 모릅니다. 확인하려면 화면이나 설명서를 봐야 하고, 주행 중 화면 조작은 그 자체로 위험합니다"그거 타이어 공기압이야, 다음 휴게소에서 보자"
내릴 때 창문을 열어 두거나 뒷좌석 물건을 두고 내립니다"창문 열려 있어", "뒤에 가방 챙겨"
긴 운전이 지루하고, 힘든 날 퇴근길은 외롭습니다말동무, "오늘 고생했어"

왜 몸이 있는 감성 봇인가

  • 대시보드 위 로봇은 스마트폰보다 부담을 줄이고 친밀감을 높였습니다(MIT AIDA, VW 협력 시뮬레이터 연구). 표정과 고갯짓은 화면 글보다 한눈에 읽힙니다.
  • 차 안 캐릭터의 인기는 이미 확인됐습니다. NIO NOMI는 대시보드 위 머리가 말하는 쪽으로 돌고 표정을 짓습니다. 하지만 NIO 차에 붙박인 내장형입니다.
  • 글레오는 차의 목소리 비서입니다. 몸이 있는 감성 동승자는 글레오가 대신할 수 없는 자리입니다.

왜 커넥트 앱 + 연결 규약인가

  • 봇은 차를 직접 읽을 수 없습니다. Pleos는 앱만 플랫폼 API로 차에 접근하게 합니다(하드웨어 직접 접근 금지). 봇이 차와 운전자를 살피려면 차 데이터를 받아 줄 앱, 곧 허브가 필요합니다.
  • 봇은 앞으로 다양해집니다. 캐릭터 로봇, 센서 모듈, 카메라 큐브, 브랜드 굿즈 봇이 나올 수 있습니다. 봇마다 앱을 따로 만들면 운전자도 제조사도 힘듭니다. 앱 하나와 규약 하나로 여러 봇이 Pleos 차 데이터를 안전하게 쓰게 합니다.
  • 차와 봇은 서로의 빈자리를 채웁니다. 차는 앱에 실내 CO₂·습도·미세먼지 값과 실내 카메라 영상을 주지 않습니다. 봇의 센서가 그 감각을 더하고, 허브가 차 정보와 합쳐 해석합니다. 예: 습도(봇) + 창문 닫힘·비·밤(차) → "유리에 김 서릴 것 같아요."
  • 그래서 정해야 할 것은 주고받는 약속, 곧 규약입니다. 봇이 자기 몸을 어떻게 설명하고, 차와 봇의 정보를 어떤 말로 주고받고, 해석한 결과를 봇의 몸에 어떻게 돌려줄지를 하나의 규약으로 정합니다.

5-2. 구조: 허브·봇·두뇌

차가 주는 정보(Vehicle·음성 SDK) + 봇이 주는 정보(센서) → 커넥트 앱(허브): 번역 · 해석 → 규약 → 봇들: 각자 몸으로 표현 / 두뇌(AI): 말투·맥락 해석, 문장

해석의 중심은 차 안의 커넥트 앱입니다. 차와 봇의 정보를 모으고, 안전과 바로 관련된 상황은 앱 안 규칙으로 정하므로 인터넷이 끊겨도 동작합니다. 듣기와 말하기는 차 안의 Pleos 음성 엔진이 합니다. AI는 말투와 맥락을 해석하고, 연결된 봇의 몸 설명 안에서 피드백을 고릅니다. 봇은 받은 피드백을 자기 몸으로 표현합니다.
  • 인터넷이 끊기면: 출발·도착·경고·휴식 한마디는 앱 안에 정해 둔 말을 Pleos 목소리로 합니다. 자유 대화만 쉽니다.
  • 봇 연결 방식: 프로토타입은 봇이 Wi-Fi로 클라우드 중계에 붙습니다. 최종 목표는 블루투스로 커넥트 앱에 바로 붙는 방식입니다. 규약 메시지는 같고 전송 방법만 바뀝니다.
  • 차량 LLM이 앱에 공개되면 클라우드 AI 대신 그것을 씁니다.

6. 기대효과 및 발전 가능성

운전자에게 주는 가치

  • 혼자 운전해도 옆에서 차와 나를 같이 살펴 주는 동승자가 생깁니다.
  • 화면을 보지 않고 봇의 표정과 짧은 말로 상황을 압니다. 차가 모르는 실내 공기·김서림까지 봇이 알려 줍니다.
  • 마음에 드는 봇을 골라 붙일 수 있고, 봇이 없어도 화면 속 스노봇으로 시작할 수 있습니다.

봇 제조사에 주는 가치 바뀜

  • 차 데이터를 직접 다루지 않고 규약 하나로 Pleos 차에 맞는 봇을 만들 수 있습니다.
  • 차 정보 번역과 해석은 허브가 맡으므로, 제조사는 봇의 몸·표정·센서에 집중합니다.

현대차그룹에 주는 가치

  • Pleos 생태계가 앱 마켓을 넘어 차 안 하드웨어(봇) 생태계로 넓어집니다. 규약을 지키는 봇은 모두 Pleos 차 데이터를 쓰고, 봇의 센서 정보는 거꾸로 차가 모르던 실내 상황을 알려 줍니다.
  • 글레오의 미리보기 실험실: 차에 바로 넣기엔 검증이 더 필요한 기능(말 거는 때, 휴식 권유 말투, 새 센서)을 원하는 사용자에게 봇으로 먼저 시험하고, 동의한 사용자의 익명 통계로 효과를 확인해 검증된 것만 글레오로 넘깁니다.
  • 차에 센서를 더하기 전에 봇 센서로 쓸모를 미리 확인합니다.

타깃 고객

  1. 출퇴근·장거리를 혼자 운전하는 Pleos 차량 운전자 (졸음·경고등·말동무)
  2. 운전자 모니터링 같은 고급 감지 기능이 없는 트림의 차주 (봇으로 기능 확장)
  3. 캐릭터·감성 제품을 좋아하는 운전자 (봇 수집·꾸미기)
  4. 봇·센서·캐릭터 굿즈를 만드는 하드웨어 제조사 (규약 참여)

2부 · 연결 규약

봇 커넥트 규약 (Bot Connect Protocol) v0.3 (2026-11-04)

차(Pleos)와 대시보드 위 감성 봇이 정보와 기능을 주고받는 약속이다. 모양과 몸이 달라도 이 규약을 지키면 같은 앱(허브)에 붙는다. 스노봇은 이 규약을 따르는 첫 번째 봇이다. 이름은 봇 커넥트 규약(Bot Connect Protocol, BCP) 으로 정했다(11/4). 여러 봇을 위한 규약이라 스노봇 이름을 넣지 않았다. 메시지의 버전 필드는 bcp. 시연용 두 번째 봇은 LED 큐브(얼굴 없이 빛·효과음·습도 센서)다.

규약이 정하는 것은 네 가지다.

부분정하는 것절
① 연결봇과 차(허브)가 서로 찾고, 짝을 맺고, 말을 주고받는 길2
② 봇 설명봇의 몸(눈꺼풀·눈썹·목·LED·스피커·마이크…)과 센서를 허브가 이해하는 형식3
③ 정보와 해석차가 주는 정보 + 봇이 주는 정보 → 허브와 AI 가 상황으로 해석4, 5
④ 피드백해석한 상황을 봇의 몸에 맞는 표현·말·동작으로 돌려주는 방법6

v0.2에서 바뀐 것: 봇 설명을 감정 목록에서 몸 부위와 움직일 수 있는 범위로 넓혔다. 봇이 주는 정보(카메라·습도 등)를 정보 모델에 넣고 해석 흐름을 정의했다. 피드백을 의도·몸짓·부위 직접 제어 세 단계로 나눴다. 안전 규칙·성격은 13절 고려사항으로 옮겼다.

0. 원칙1. 구성과 MCP 대응2. 연결3. 봇 설명 (hello)4. 정보 모델: 누가 무엇을 주는가5. 해석: 정보를 상황으로6. 피드백: 봇의 몸에 맞게 돌려주기7. 허락 (welcome)8. 확장과 버전9. 적합성 시험 (봇 시험기)10. 지금 구현 (2026-11-04)11. 구현 계획 (11/15 접수까지)12. 열린 항목13. 추가 기능 고려사항

0. 원칙

  1. 봇은 몸과 감각을, 허브는 차와 해석을 맡는다. 봇은 자기 몸으로 표현하고 자기 센서로 느낀다. 허브(Pleos 커넥트 앱)는 차를 읽고, 차와 봇에서 온 정보를 합쳐 해석하고, 피드백을 보낸다. 문장과 미묘한 해석은 AI(두뇌)가 돕는다.
  2. 차 데이터는 허브만 읽는다. Pleos 는 앱만 플랫폼 API 로 차에 접근하게 한다(하드웨어 직접 접근 금지). 봇은 허브가 번역해 준 정보만 받는다.
  3. 봇은 차에 없는 감각을 더한다. 차는 앱에 실내 CO₂·습도·미세먼지 값과 실내 카메라 영상을 주지 않는다(05). 봇의 센서가 그 빈자리를 채운다.
  4. 봇의 몸을 설명받아 그 몸에 맞게 피드백한다. 허브와 AI 는 봇이 선언한 부위와 범위 안에서만 명령한다. 봇을 바꾸면 피드백도 바뀐다.
  5. 원본은 봇 안에, 결과만 밖으로. 카메라·마이크가 있는 봇은 처리한 결과("눈 감김 2초", "B3 C-12")만 보낸다. 원본 영상·소리는 운전자가 따로 허락할 때만.
  6. 전송과 상관없다. 같은 메시지를 블루투스·클라우드·같은 Wi-Fi 로 보낸다.

4-1. 차가 주는 정보 (허브 → 봇·AI, context)

허브가 Pleos SDK 로 읽은 신호를 봇이 알아듣는 주제로 바꾼다. 봇은 welcome 에서 허락받은 주제만 받는다.

5. 해석: 정보를 상황으로

허브는 차 정보와 봇 정보를 합쳐 상황을 만든다. 안전과 바로 관련된 것은 허브의 규칙이 정해진 대로 빠르게(인터넷 없이) 판단하고, 말투·미묘한 해석은 AI 가 돕는다.

flowchart LR
  C["차가 주는 정보<br/>car.*"] --> F["허브: 합치기"]
  O["봇이 주는 정보<br/>observe"] --> F
  F --> R["규칙 해석<br/>빠름 · 오프라인 · 안전"]
  F --> A["AI 해석<br/>말투 · 맥락 · 대화"]
  R --> S["상황"]
  A --> S
  S --> P["피드백 고르기<br/>봇 설명에 맞춰"]

상황 형식 (허브 안, AI 에 주는 값):

{ "situation": "fog_risk", "severity": "guide", "evidence": ["obs.env.humidity=78", "car.cabin.recirc=true", "car.outside.night=true"],
  "suggest": "외기로 바꾸거나 에어컨 켜기" }

창문 닫힘, 비(와이퍼), 밤습도 75% 이상fog_risk 앞유리 김서림 우려걱정 표정 + "유리에 김 서릴 것 같아요. 에어컨 켜 볼까요?"

6. 피드백: 봇의 몸에 맞게 돌려주기

피드백은 세 단계다. 봇은 1단계는 반드시 처리하고, 2·3단계는 선언한 부위만 처리한다.

단계메시지허브가 정하는 것봇이 정하는 것
1 의도express감정·강도·이유어느 부위를 어떻게 움직일지 전부
2 몸짓gesture정해진 몸짓 이름 또는 짧은 순서몸짓을 자기 속도로
3 부위 직접pose부위별 목표값과 시간범위 자르기, 부드럽게 잇기

6-1. 의도 (express)

{ "bcp": "0.3", "type": "express", "emotion": "worried", "intensity": 0.7, "reason": "fog_risk", "hold_ms": 4000 }

공통 감정 어휘 (봇은 최소 neutral·happy·worried·alert 를 표현해야 한다):

감정쓰는 때스노봇LED 큐브
neutral기본눈 보통, 정면흰빛 은은하게
happy기쁨, 도착눈웃음, 눈썹 올림노란빛 밝아짐
greet인사, 출발눈웃음 + 끄덕노란빛 두 번 깜빡
worried걱정, 경고등, 답답함눈썹 처짐주황빛 숨쉬기
sleepy졸림, 오래 운전눈꺼풀 내림파란빛 느리게
alert놀람, 급한 알림, 듣는 중눈 크게, 눈썹 올림흰빛 빠르게 깜빡
guard삐짐(장난)눈 가늘게, 고개 돌림보랏빛

없는 감정이 오면 봇이 가까운 것으로 바꾼다(greet→happy, sleepy·guard→neutral).

6-2. 몸짓 (gesture)과 보기 방향

{ "bcp": "0.3", "type": "gesture", "name": "nod" }
{ "bcp": "0.3", "type": "gesture", "name": "look", "at": "driver" }
{ "bcp": "0.3", "type": "gesture", "steps": [ { "part": "head", "pan": -30, "ms": 300 }, { "part": "head", "pan": 0, "ms": 400 } ] }

look 의 at 은 driver · passenger · rear · road · center. 봇은 2-1의 자리 정보로 각도를 계산한다. 같은 "운전자 쪽 보기"도 대시보드 가운데 봇과 조수석 쪽 봇은 다른 각도가 된다.

6-3. 부위 직접 (pose)

{ "bcp": "0.3", "type": "pose", "targets": { "eyelid.open": 0.4, "brow.tilt": 0.6, "head.tilt": -8 }, "ms": 500 }
{ "bcp": "0.3", "type": "pose", "targets": { "ring.color": "#FF8A00", "ring.pattern": "breathe" }, "ms": 0 }

6-4. 말하기·듣기 (say · listen)

{ "bcp": "0.3", "type": "say", "id": 41, "text": "유리에 김 서릴 것 같아요. 에어컨 켜 볼까요?", "urgency": "guide" }
{ "bcp": "0.3", "type": "listen", "id": 42, "max_ms": 8000 }
  • say: 봇의 speaker.voice 에 따라 허브가 소리를 보내거나(hub_stream), 글자만 보내거나(bot_tts), 효과음만 낸다(chime). 스피커가 없으면 차 스피커(Pleos TTS)로.
  • listen: 차 안에서는 보통 차의 마이크(Pleos STT)로 듣는다. 봇 마이크로 들을 때는 봇이 소리를 보내거나(hub_stream) 글자(heard)를 보낸다.

6-5. AI 에 봇의 몸 알려 주기

허브는 연결된 봇의 parts·expressions·actions 를 AI 가 고를 수 있는 도구 목록으로 바꿔 준다(MCP 에서 도구 설명이 모델에게 가는 것과 같다). 예: 스노봇이 붙어 있으면 AI 는 "눈썹을 내리고 운전자 쪽을 본다"를, LED 큐브만 있으면 "주황빛으로 숨쉰다"를 고른다.

7. 허락 (welcome)

{ "bcp": "0.3", "type": "welcome", "hub": "Pleos Connect", "granted": ["car.motion", "car.cabin", "trip"],
  "denied": ["driver.state"], "mode": "drive", "observe_period_s": { "env": 10 } }
  • 운전자는 앱에서 봇마다 받는 정보를 보고 끌 수 있다(앱 권한과 같은 방식). 예: "이 봇은 운전 상황·실내 상태를 받습니다. 위치는 받지 않습니다."
  • 카메라·마이크 결과를 보내는 봇은 연결할 때 운전자가 따로 허락해야 한다.

8. 확장과 버전

  • 새 부위·센서·감정은 규약 버전을 올려 더한다.
  • 제조사 고유 기능은 x-회사.이름(예: x-snowbot.scarf_wave)으로 선언한다. 허브는 몰라도 AI 에 이름과 설명을 넘길 수 있다.
  • v0.2 호환: express 의 expr(= emotion)·head(= gesture), event(= observe), capabilities(= parts·sensors)를 계속 받아들인다.

13. 추가 기능 고려사항
