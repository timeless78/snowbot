# 모의 심사 (2026-11-01)

심사위원 역할의 에이전트 3명이 서로의 결과를 보지 않고 따로 평가했다. 기준은 [00-contest-rules.md](00-contest-rules.md)의 1차 서류 심사 4항목이고, 항목마다 25점 만점으로 가정했다. 대상은 [01-proposal.md](01-proposal.md), [README](../../README.md), `app/`·`server/` 코드다.
코드 사실 중 아래 네 가지는 Claude가 직접 다시 확인했다: NaviHelper 코드 없음 · 서비스 없음 · `onStop`에서 연결 끊음 · `distractionOptimized` 선언만 있고 `CarUxRestrictions` 리스너 없음.

## 세 명이 함께 짚은 약점

1. **Pleos SDK 활용이 얇다.** 실제로 쓰는 것은 Vehicle SDK의 기어와 `DRIVER_ATTENTION` 두 가지뿐이다. NaviHelper, Gleo, TTS/STT, FusedLocation은 코드에 없다. 대화의 핵심인 음성 인식, 대답, 목소리는 외부 API(ElevenLabs·Claude)가 맡는다.
2. **앱 화면이 열려 있을 때만 먼저 말을 건다.** `onStop`에서 서버 연결을 끊고, 백그라운드 서비스도 없다. 그래서 Retention 35%의 근거("출발·도착에 먼저 말 건다")가 코드와 맞지 않는다.
3. **사업성 숫자가 매출로 이어지지 않는다.** MAU의 입력값(설치율 5%, 월 사용 40%)에 근거가 없다. 모듈 판매가, 원가, 구매율, 구독 가격도 없다.
4. **하드웨어 리스크가 기획서에 없다.** PLA 내열, 에어백·시야를 피한 고정, KC·전파 인증, 양산 원가가 빠져 있다. 내부 README에는 적혀 있다.

## 한두 명이 짚은 점

- `distractionOptimized=true`를 선언했지만 `CarUxRestrictions` 리스너가 없다. 앱 마켓 심사에서 리젝 사유가 될 수 있다.
- Virtual Console에 `DRIVER_ATTENTION`이 없어 디버그 명령으로 값을 넣어야 한다. PT에서 차 신호로 보여 줄 수 있는 것은 기어뿐이다.
- 모든 기능이 클라우드에 의존한다. 현장 네트워크가 끊기면 시연을 할 수 없다.
- 기획서가 음성 안내의 인지 부담(3.34/5)을 인용해 놓고, 말을 거는 앱을 제안한다. 총 간섭량을 어떻게 줄이는지 설명이 필요하다.
- 2-1절 "글레오의 미리보기 실험실"은 주최사의 논리다. 운전자가 이 앱을 깔 이유가 아니다.
- 기능표에서 로봇 모듈이 빠지면 공기질과 주차 기능이 사라진다. 기능표를 "앱만으로 되는 것"과 "모듈이 더하는 것"으로 나눠야 한다.
- 대시보드 캐릭터는 선례가 있다(NOMI, Kirobo Mini, MIT AIDA). 기획서에 이 선례와의 차이가 없다.

## 강점

- 접수 시점에 앱이 실제로 동작한다(에뮬레이터 화면, 서버 테스트 20개, 응답 시간 실측). 세 명 모두 짚었다.
- "무엇을 말할까"보다 "지금 말해도 되나, 얼마나 말할까"를 먼저 정한다는 차별점이 한 문장으로 분명하다.
- SDK 한계를 숨기지 않는다. 앱이 로봇 없이도 동작한다.
